# Database Design

Single PostgreSQL database (extensions: `pgvector`, `pg_trgm` for fuzzy admin search, built-in `tsvector` for full-text). Drizzle ORM/Drizzle Kit for schema + migrations (see [ADR-0007](decisions/0007-drizzle-orm.md)).

Conventions used throughout:
- `id`: `uuid` primary key, generated by the app (not serial) — safe to reference before insert, no enumeration leakage.
- `createdAt`, `updatedAt`: on every table.
- `deletedAt` (soft delete): only on entities an admin can accidentally remove and might want back (`Project`, `Experience`, `Education`, `Certification`, `Achievement`, `KnowledgeDocument`). Not on ephemeral/append-only tables (`ChatMessage`, `UsageRecord`, `AuditLog`, `AbuseEvent`) — deleting those defeats their purpose.
- `status`: `DRAFT | PUBLISHED | ARCHIVED` enum on every publicly-rendered content entity.

## 1. Admin & Auth

```
AdminUser
  id, email (unique), passwordHash (argon2id), role (SUPER_ADMIN|EDITOR|ANALYST, default SUPER_ADMIN),
  isActive, lastLoginAt, createdAt, updatedAt

AdminSession
  id, adminUserId (fk), expiresAt, ipAddress, userAgent, createdAt, revokedAt (nullable)
  index: (adminUserId), (expiresAt)  -- for cleanup sweep
```

RBAC is enum-based today (single row exists), but every admin API route checks `role` against a required-permission map in `lib/auth`, so adding `EDITOR`/`ANALYST` restrictions later is a config change, not a schema or route change.

## 2. Portfolio content (CMS)

```
Profile            -- singleton (one row): name, headline, tagline, avatarUrl, location, availability, socialSummary
About               -- singleton: bio (rich text), missionQuote, highlights (jsonb: [{icon,title,description}])
Experience          -- id, role, company, period (startDate, endDate nullable=current), description, technologies (jsonb string[]),
                       displayOrder, status, deletedAt
Education           -- id, institution, degree, field, period, description, displayOrder, status, deletedAt
Skill               -- id, name, category (enum: LANGUAGE|FRAMEWORK|DATABASE|TOOL|PLATFORM|SOFT_SKILL), proficiency (1-5, nullable),
                       displayOrder, status
Project             -- id, title, slug (unique), description, longDescription, coverImageUrl, liveUrl, githubUrl,
                       featured (bool), displayOrder, status, deletedAt
ProjectTechnology   -- id, projectId (fk), technology (string), displayOrder      -- normalized so tags are queryable/reusable
ProjectImage        -- id, projectId (fk), url, altText, displayOrder             -- galleries beyond the single cover image
Certification       -- id, name, issuer, issueDate, expiryDate (nullable), credentialUrl, displayOrder, status, deletedAt
Achievement         -- id, title, description, date, displayOrder, status, deletedAt
SocialLink          -- id, platform (enum: GITHUB|LINKEDIN|TWITTER|EMAIL|WEBSITE|OTHER), url, label, displayOrder, isVisible
Resume              -- id, fileUrl (object storage, not bytea — see §6), fileName, fileSizeBytes, isActive, version, uploadedAt
```

Why normalized here but not everywhere (per master prompt §5 — don't over-normalize): `ProjectTechnology` and `Skill` are separate tables because they're genuinely repeated, filterable, and reused across the tag cloud / skills matching in RAG metadata. `About.highlights` stays a `jsonb` array because it's a small, fixed-shape, never-queried-independently blob — a separate table would be normalization for its own sake.

## 3. Layout & theming

```
PortfolioSection
  id, key (enum: HERO|ABOUT|EXPERIENCE|EDUCATION|SKILLS|PROJECTS|CERTIFICATIONS|ACHIEVEMENTS|SERVICES|CONTACT),
  isVisible (bool), displayOrder (int), createdAt, updatedAt
  -- single source of truth for what renders on the public page and in what order; the public page component
  -- iterates this table, not a hardcoded array.

Theme
  id, name, basePresetId (fk to ThemePreset, nullable if fully custom), isActive (bool, only one row true at a time),
  config (jsonb: ThemeConfig — colors/typography/layout/components/effects, see architecture.md §14 of the master prompt),
  createdAt, updatedAt

ThemePreset
  id, name (Modern|Minimal|Developer|Corporate|Glass|Custom...), config (jsonb, immutable "factory" defaults), createdAt
  -- Theme.basePresetId references this; customizing never overwrites the preset row (master prompt §16) —
  -- "Customize" clones the preset's config into a new Theme row.
```

`ThemeToken` (a normalized token table) was considered and rejected: theme config is read as a whole object on every page load and written as a whole object from the theme builder — there is no query pattern that benefits from splitting it into rows, so it stays `jsonb` (avoids over-normalization per master prompt §5).

## 4. AI knowledge (separate from public content, per master prompt §17-18)

```
KnowledgeDocument
  id, sourceType (enum: PROFILE|ABOUT|EXPERIENCE|EDUCATION|SKILL|PROJECT|CERTIFICATION|ACHIEVEMENT|RESUME|FAQ|CUSTOM),
  sourceEntityId (nullable — points at the owning row, e.g. Project.id; null for CUSTOM/FAQ),
  includeInRag (bool, default true), additionalContext (text, admin-authored extra knowledge not shown publicly),
  faqs (jsonb: [{question, answer}]), priority (int, default 0 — higher wins in context-builder tie-breaks),
  visibility (enum: PUBLISHED|DRAFT — only PUBLISHED is ever retrievable by the public chatbot),
  version (int, incremented on every content change that affects this document),
  indexStatus (enum: PENDING|INDEXING|INDEXED|FAILED), lastIndexedAt, chunkCount, indexError (text, nullable),
  createdAt, updatedAt, deletedAt

KnowledgeChunk
  id, documentId (fk), content (text), embedding (vector(1536)), tokenCount,
  metadata (jsonb: {section, title, contentType, priority, sourceType, sourceEntityId, version}),
  contentTsv (tsvector, generated column from `content`, for keyword search)
  indexes: HNSW on `embedding` (cosine ops), GIN on `contentTsv`, btree on (documentId)
```

Every content-editing table above (Experience, Project, etc.) has a 1:1 (or 1:many for FAQ-style) relationship to `KnowledgeDocument` via `sourceEntityId` — this is the mechanism behind master prompt §17: each content entity carries its own "AI Knowledge" config (include-in-RAG toggle, extra context, FAQs, priority) surfaced as a tab/section in that entity's admin edit screen, without polluting the entity's own table with AI-specific columns.

## 5. Visitors & chat

```
Visitor
  id, name (nullable), email (nullable), visitorType (enum: RECRUITER|HR|DEVELOPER|CLIENT|POTENTIAL_CLIENT|COMPANY|STUDENT|OTHER, nullable),
  purpose (text, nullable), consentGivenAt, ipHash (hashed, not raw IP — privacy), createdAt

ChatSession
  id, visitorId (fk, nullable — a session can start before visitor info is collected),
  status (enum: ACTIVE|ENDED|RATE_LIMITED|BLOCKED), lastActivityAt, messageCount, totalTokens, createdAt
  (createdAt doubles as "started at" — a session is always "started" the instant its row exists, so a separate startedAt column would just duplicate it)

ChatMessage
  id, sessionId (fk), role (enum: VISITOR|ASSISTANT|SYSTEM), content (text),
  intent (enum: PORTFOLIO_QUESTION|GENERAL_QUESTION|ABUSE, nullable — set by the LangGraph intent node),
  retrievedChunkIds (jsonb: uuid[], nullable — which KnowledgeChunks were used, for grounding audit),
  requestId (uuid, correlates to observability trace), createdAt
```

## 6. Resume storage

`Resume.fileUrl` points at object storage (local disk volume in dev via a small file-serving route; S3 in production — see [deployment.md](deployment.md)), never `bytea` in Postgres, per master prompt §56. Only `isActive = true` row is served publicly; uploading a new resume creates a new versioned row rather than overwriting.

## 7. Usage, cost, evaluation, observability, security

```
UsageRecord
  id, requestId (uuid), sessionId (fk, nullable), model, inputTokens, outputTokens, totalTokens,
  estimatedCostUsd (numeric), latencyMs, createdAt
  index: (createdAt) -- for dashboard date-range rollups

EvaluationDataset
  id, name, version, createdAt
EvaluationCase
  id, datasetId (fk), question, expectedAnswer, expectedSources (jsonb: string[])
EvaluationRun
  id, datasetId (fk), model, promptVersion, retrievalConfig (jsonb snapshot), startedAt, completedAt, status
EvaluationResult
  id, runId (fk), caseId (fk), actualAnswer, retrievalRelevance, contextRecall, answerRelevance,
  faithfulness, answerCorrectness, hallucinated (bool), notes, createdAt

AuditLog
  id, adminUserId (fk, nullable), action (string, e.g. "project.update", "theme.publish", "admin.login"),
  targetType, targetId (nullable), metadata (jsonb), ipAddress, createdAt

AbuseEvent
  id, sessionId (fk, nullable), ipHash, kind (enum: RATE_LIMIT|TOKEN_LIMIT|PROMPT_INJECTION|OVERSIZED_INPUT|OTHER),
  detail (text), createdAt
```

## 8. Indexing strategy (per master prompt §80-81)

- Every foreign key gets a btree index (Drizzle Kit default via `references()` + explicit `index()` calls where not auto-created).
- `KnowledgeChunk.embedding`: HNSW index (`pgvector` — better recall/latency tradeoff than IVFFlat at this scale and doesn't require a training step on an empty table).
- `KnowledgeChunk.contentTsv`: GIN index for full-text.
- `UsageRecord.createdAt`, `ChatMessage.createdAt`, `AuditLog.createdAt`: btree, since every admin dashboard query is a date-range filter.
- All admin list views (`Project`, `Visitor`, `ChatSession`, `ChatMessage`, `UsageRecord`, `AuditLog`, `KnowledgeDocument`) are paginated (keyset pagination on `createdAt` + `id`, not `OFFSET`, to stay performant as tables grow) per master prompt §81.
- No index added speculatively — each one above is justified by a named query pattern (dashboard rollups, admin tables, vector/keyword retrieval, FK lookups).

## 9. What's explicitly NOT modeled (avoiding over-engineering, per master prompt §5)

- No generic "CMS field" / EAV table — every content type gets real, typed columns, since the field set per entity is fixed and known.
- No separate `Tag` table shared across all entity types — tags are entity-scoped (`ProjectTechnology`) because cross-entity tag reuse isn't a real requirement here.
- No multi-tenant columns (`organizationId` etc.) — this is a single-owner portfolio, not a multi-tenant SaaS.
