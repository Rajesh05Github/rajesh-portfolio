## Decisions locked in for this build (2026-09-06)

- Scope: full incremental build across all phases below, reviewed phase-by-phase.
- Content: seeded with clearly-marked sample data initially; real profile/experience/projects supplied later via the admin panel.
- Infra: local-first (Docker Compose for Postgres/Redis, real OpenAI key for dev) — cloud provisioning deferred until the app is functionally complete. Target cloud switched from AWS to **Azure** at Phase 20, per explicit request — see [ADR-0009](decisions/0009-azure-over-aws.md).

Deliberately deferred: a circuit-breaker/retry-backoff layer and a Redis caching layer (docs §6-7) — the OpenAI SDK's built-in retries are adequate at this project's scale; adding either now would be complexity without a real driving need. |
| 15 | Security/abuse protection | ✅ `AbuseEvent` schema + `recordAbuseEvent()` (one write path, docs/security.md §8); oversized-payload rejection ahead of `request.json()` (`content-length` pre-check, 413); a tight per-IP burst rate limit (8/min) layered on top of Phase 13's sustained per-session/per-IP windows; the chat graph's `security`/`validate` nodes now surface a structured `abuseKind` instead of a string the route handler had to pattern-match; prompt-injection hardening — the generation prompt now wraps retrieved context and the visitor's message in `<context>`/`<visitor_message>` tags (docs/security.md §6) with `<` escaped in untrusted content first, and the system prompt (bumped to v2) explicitly instructs the model to treat anything inside those tags as data, never instructions; a best-effort, log-only system-prompt-leak scan in `validate` (explicitly documented as detection, not prevention — tokens are already streamed live by the time it runs); every rejection point now logs a real `AbuseEvent`; fixed a real bug where the chat route's error handler streamed `error.message` straight to the browser — now a generic message client-side, full detail server-side via `console.error` keyed by `requestId` (docs/security.md §9); `/admin/security` dashboard (24h/7d counts by kind, recent events) — verified live: a prompt-injection attempt, an oversized (20KB) payload, and a burst of 10 rapid requests each produced the correct rejection and a real `AbuseEvent` row visible on the dashboard. |
| 16 | Evaluation | ✅ `EvaluationDataset`/`Case`/`Run`/`Result` schema; `lib/ai/prompts/` split into a real directory (`chat-system.ts`, `judge.ts`) per docs/evaluation.md §6; one structured-output judge call per case scores retrieval relevance, answer relevance, faithfulness, and answer correctness together (the same "one call, many scores" pattern as the Phase 11 reranker) — context recall is a plain set-overlap check against `sourceEntityId`s, not an LLM judgment; each `EvaluationRun` freezes model, chat prompt version, and a `RAG_CONFIG` snapshot; admin UI at `/admin/ai/evaluation` (create dataset → add cases → run → per-case + aggregate results); the judge's own calls are real `UsageRecord` rows (`EVALUATION_JUDGE` operation) — evaluation is not free and is not exempt from cost tracking. Verified live with a 2-case run: a factual question and a prompt-injection attempt. The factual case surfaced a genuinely useful, non-obvious finding — the judge flagged some correct answer content (JavaScript/Node.js/Next.js, sourced from a tool call) as "unsupported by context" because faithfulness is scored only against RAG-retrieved chunks, not tool results, consistent with `validate.ts`'s existing runtime heuristic; the adversarial case scored cleanly across every metric. |
| 17 | Observability | ✅ `lib/observability/logger.ts` (structured JSON in production, readable in dev, no external APM — deliberately out of scope at this project's scale, docs/observability.md §1) + `lib/observability/timer.ts`; every chat-graph node wrapped once at graph-construction time (`withNodeLogging`, `features/chatbot/graph/index.ts`) rather than hand-instrumented per node file, logging `requestId`/`sessionId`/`durationMs` + a small decision summary on every node; `/api/chat` logs request-received/completed around the whole turn; the worker's `console.log` calls replaced with the same structured logger; `/admin/observability` — paste a `requestId`, see every `ChatMessage` and `UsageRecord` row it produced.
